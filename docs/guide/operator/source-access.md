# 调用方凭据与路由授权

对外提供的接口、签名、消息结构和错误处理说明见[来源消息接入 SDK 文档](../../sdk/index.md)。

WeKeeper 是上游接收服务，Linjian 是下游调用方。所有请求均由 Linjian 主动发起：提交消息、检查凭据和路由、查询回执。WeKeeper 不回调下游，不探测或查询 Linjian 在线状态。

Docker 部署使用本功能前，由部署人员按 [Docker 主密钥配置说明](../../runbooks/docker.md#调用方凭据主密钥-首次配置与已有部署更新)设置并保存 `WEKEEPER_SOURCE_MASTER_KEY_V1`；它仅供 WeKeeper 内部加密存储，不交给下游。`make dev-embedded` 会为本次临时数据库自动配置；Docker 不会自动生成。

“消息接收管理 → 调用方凭据”属于消息接收业务，目前由系统管理员维护，不依赖企业微信或移动端工作空间。

在“调用方凭据”新增记录，填写平台名称、凭据备注、状态和有效期。每个下游对应一条调用方凭据，保存时生成唯一的凭据 ID（key_id）和签名密钥（secret）；无需另外创建平台，也不配置下游地址、可信网址或内容路径前缀。WeKeeper 不保存学校目录。

下游只需填写以下三项，凭据 ID 可直接复制：

| 页面字段 | 下游配置字段 | 用途与获取方式 |
| --- | --- | --- |
| 凭据 ID | `key_id` | 同时标识调用方与其凭据，放入签名请求头 `X-Source-Key-Id`；不是签名密钥 |
| 签名密钥 | `secret` | 用于请求签名，与 `key_id` 配套；在凭据详情点击“查看密钥”查看、复制或下载，可重复核对 |
| WeKeeper 服务地址 | `origin` | 本次部署对下游公开的 WeKeeper HTTPS 地址，由部署人员提供 |

给下游的凭据是 **`key_id` 与 `secret` 这一对**，无需额外填写调用方 ID。路由的 `route_id` 在凭据子项中选择，用于消息分发，不代替签名凭据。WeKeeper 存储主密钥 `WEKEEPER_SOURCE_MASTER_KEY_V1` 仅供内部使用，不交付给下游。

左侧“消息接收管理”分组提供“调用方凭据”入口。新增凭据后，在该凭据行打开“路由”子项，填写单位名称、路由备注和状态；创建时系统在一次操作中建立该平台下的单位、路由并授权当前凭据。调用方归属自动带入，无需另行选择或填写 ID。route_id 由服务端生成且保持不变。

子项只列当前调用方的路由，支持搜索、状态筛选和分页。可编辑单位名称、路由备注和启停状态，也可对当前凭据授权或撤销授权；关联双方必须属于同一调用方。凭据签发后与对应下游绑定，不提供轮换功能。

列表支持标识或名称、凭据 ID、状态及失效时间上界筛选。详情区分凭据备注与各路由备注。创建后打开“编辑”，在“下游连接配置 → 签名密钥（secret）”点击“查看密钥”，可查看、复制密钥或下载包含 key_id、secret 的凭据文件，再交给下游填写。可隐藏并反复查看同一份 secret，已通过后台命令交付的凭据也可查看；查看不会重新签发或更换密钥。关闭详情后隐藏密钥，每次查看记录操作人、凭据及请求审计，审计不保存密钥值。Linjian 管理员另行填写部署人员提供的 WeKeeper HTTPS 地址。

凭据编辑可以修改平台名称、备注、状态和有效期，不能转移调用方归属。路由授权在凭据行内的“路由”入口中维护，不再手工粘贴路由 ID。修改版本冲突时刷新后核对；撤销授权只取消关联；删除凭据则永久删除整条凭据、其关联路由和路由授权，保留历史收件、任务和审计。

有效期支持“长期有效”和指定失效时间。新增默认长期有效，仍须满足生效时间与启用状态；可随时改为指定失效时间。长期有效在接口中使用 `valid_until: null`，不使用远期日期代替。

删除凭据需确认，凭据及其消息分发路由不可恢复，既有历史收件、任务和审计保留；旧 key 随即失效。升级迁移会清理此前已软删除的凭据及其路由。下游自行构造完整正文 `content`，标题、链接与换行均包含其中；WeKeeper 不拼接来源消息，不执行 HTTPS URL 校验，不抓取、不回调，也不要求登记可信域名。正常消息不需要逐条调用认证或办理人工审批。接入事务成功后立即返回已接收，不等待敏感词、广告或发送配置检查；下游接收回执不包含内部处理和发送状态。内部发送结果仅供系统管理员查询；配置并启用自动执行后，WeKeeper 会创建对应通道任务；收件、创建任务和真实发送是不同阶段。

## 下游消息结构

POST `/api/v2/source-events` 使用现有签名请求头与 `application/vnd.api+json`。下游自行生成完整的纯文本 `content`：

```json
{
  "data": {
    "type": "source-events",
    "id": "00000000-0000-0000-0000-000000000001",
    "attributes": {
      "event_id": "00000000-0000-0000-0000-000000000001",
      "schema_version": 2,
      "route_id": "assigned-route",
      "event_type": "content.upsert",
      "occurred_at": "2026-11-16T00:00:00Z",
      "content": "活动通知\n明天下午三点开始。\n#小程序://Linjian/示例"
    }
  }
}
```

以上字段全部必填。`event_id` 为调用方生成的 UUID，与 `data.id` 及签名请求中的幂等身份一致；`route_id` 为已授权路由；`occurred_at` 为消息发生时间，仅供审计。`content` 不得缺失、为 null 或全空白，最多 200 个字符（按 Unicode 标量计数，汉字、标点、空格和换行均计入）；超限返回 HTTP 400、错误码 `content_too_long`，提示“消息正文不能超过 200 个字符（汉字、标点、空格和换行均计入）”；空正文或全空白返回 HTTP 400、错误码 `content_empty`。总请求体最多 1 MiB。不含链接时直接填写正文。WeKeeper 保留正文中的空格、换行和链接原文；既有广告决定独立处理并保存最终发送正文。

不提供 `title`、`detail_url`、`external_content_id`、`version`、`sequence` 字段，携带这些字段会被拒绝。仅接收 `content.upsert`，名称不表示更新或覆盖旧消息；`content.withdrawn` 及其他类型返回 `400 unsupported_event_type`，不建立收件或任务。

新消息持久接收后返回 HTTP 202，相同原始请求重投返回 200。接收回执仅包含 `event_id`、固定值 `status: received` 与 `received_at`，查询与重投不因内部处理而变化。响应丢失时以原事件 ID 和完全相同的请求正文、当前签名时间及新 nonce 重投；相同事件 ID 携带不同正文返回 `409 event_conflict`。

凭据有效性与路由接入授权仍须满足；内部执行暂停、无目标、设备离线或敏感词检查不影响合法接收。认证与路由检查只返回接入授权状态，不返回内部执行开关。

## 业务单位与接收配置

业务单位在新增接入路由时一起建立，不再另建单位、受众分组或执行工作空间。系统管理员可从路由行的“执行配置”或通道“接收配置”页面，维护该单位的目标群和发送账号／候选手机。两类通道可同时启用，群只填写一个业务名称。

接收配置中的“授权自动发送新消息”是明确的链路业务授权。启用后，系统冻结新消息正文、目标、手机候选和真实执行身份，无需逐条确认。手动创建的任务继续遵守人工确认。手机离线或本地适配缺失不影响平台受理，设备按该次尝试反馈执行结果。

接收配置不要求业务人员填写版本或群独占归属。同一群可供多个配置使用，同一消息同通道的群归属由系统确定，不合并配置授权；全部手机模式下，该群由各指定手机分别执行。系统不创建工作空间存储分区或成员关系。业务单位配置由系统管理员维护，消息与回执仅系统管理员可查询。

## 收件与回执

从“消息接收管理 → 收件与回执”选择路由，查看消息 ID、处理结果、原因和接收时间，展开查看广告决定与最终正文。页面定期刷新。

每条消息独立处理。没有目标群时显示“未下发成功：没有目标群”，本条消息结束；后续补群不补发旧消息。没有合法发送资源时显示具体原因，不长期等待补配置；其他合法目标继续处理。

同一事件 ID 的相同请求返回已有回执，不重复选广告或创建任务；相同事件 ID 的不同请求正文会被拒绝。不同事件是独立即时消息。协议不包含内容版本或序号，不接收撤回通知，不执行撤回或替换。配置和广告变更只影响之后的新消息。

收件或通道受理不等于送达。发送摘要按目标统计待处理、成功、失败和不确定；手机换机不增加目标数，迟到结果仍按原尝试入账。以上发送摘要仅供系统管理员查询。下游提交成功即结束投递，无需轮询发送结果；接收查询仅用于响应丢失时核对。内部检查拦截、资源缺失或发送失败均不改变已接收事实，不要求下游重投。接入暂时不可用或限流时遵守 Retry-After。

## 敏感词拦截

敏感词拦截默认全局停用。系统管理员可在页面顶部“全局拦截设置”中操作“全局启用敏感词拦截”，一次切换对所有来源消息生效，保存后刷新页面或重启服务仍保持该状态。已有环境升级引入全局开关后同样默认停用，需要拦截时可在页面启用。

全局启用时，推送消息命中词库中的有效规则，系统停止该消息的内部分发，并在管理员处理详情中提供拦截原因；下游回执仍为已接收；检查发生在广告处理和消息分发之前。全局停用时，所有来源消息跳过敏感词检查，继续正常广告处理和分发，其他授权及发送条件仍独立校验。

全局切换不修改词库或单个词条状态，不需要逐词操作。停用期间仍可维护或导入词库，维护词库不会自动启用拦截。

从左侧“消息接收管理 → 敏感词拦截”直接进入。系统管理员可直接维护敏感词列表，列表对所有来源消息生效。

页面直接显示敏感词，可搜索、添加、编辑、删除和启停；保存后用于尚未检查的新消息。可导入 UTF-8 CSV，表头为 `word`，可选 `enabled`（true、false、1、0）；预览后确认导入。文件最多 1 MB、2000 行，重复或无效词条须先处理。敏感词最多 2000 条，词条原始长度最多 512 字节，规范化结果最多 128 个 Unicode 标量。并发修改冲突时请刷新列表，核对后重新保存。

匹配统一使用 Unicode 18.0.0 的兼容规范化与完整大小写折叠；全角、大小写及 Straße/STRASSE 等等价写法会命中。同时检查移除 Unicode 空白（包括空格和换行）后的文本，例如“诈 骗”会命中“诈骗”；不会删除零宽字符。页面历史条目展示服务端规范化文本。来源消息不会因检查被删改或打码。

全局开关和敏感词的修改用于尚未形成持久检查决定的消息（包括已接收但尚待检查的消息）；已通过检查的消息继续后续广告处理与分发，被拦截的消息不会因规则放宽恢复发送。

命中敏感词时在管理员消息和处理详情中显示拦截原因，保留检查证据供审计。

敏感词已拦截的消息不提供重新放行。正常无广告消息可直接处理，不需要等待广告配置或研发验收。

## 广告素材与投放

系统管理员从“消息接收管理 → 广告素材与投放”进入。在广告列表点击“新增”，填写名称、纯文本正文和可选的 HTTPS 链接；单个广告正文最多 140 字，汉字、标点、英文字符和 emoji 均按一个 Unicode 标量计数。超限会提示修改，不截断正文。

点击“绑定投放范围”，选择广告以及业务单位、平台或全局范围，填写生效时间和可选到期时间。单位和平台使用现有业务目录，不需要创建或选择业务资源，不需要配置路由广告池。一个范围可以绑定多个广告，每条消息最多插入一个广告。

新消息按“业务单位 > 平台 > 全局”的优先级选取当前有效范围中的广告，并在该范围内轮询。轮询对象是广告，广告轮询进度和选用次数按业务单位分别记录；即使选用平台或全局广告，也使用该业务单位自己的计数。选用次数不是曝光、送达或计费次数。

没有可用广告、拼接后的完整消息超过 200 个 Unicode 字符（汉字、标点、换行及链接均计入）或超过通道长度时，直接发送原消息，不等待、不占广告选用次数。来源消息的敏感词检查在广告选取之前完成，被拦截的消息不选择广告。广告在原消息正文后新增一个换行，直接追加广告正文及可选链接，不自动添加标题或标记；保留原文已有换行和空格，名称不会插入正文。

广告查询、计数等局部故障或超时时，在有界尝试后跳过广告并冻结原文，不要求先修广告、重推事件或重新确认。消息详情显示跳过原因；未读取选用计数时显示“未读取”，不表示次数为零。公共数据库或主消息事务不可用时仍可靠重试，不会绕过持久化和授权。

消息第一次作出广告决定后会与最终正文原子保存结果。任务创建失败后的重试、手机换机和结果未知均复用同一正文，不重复计数；已决定不投广告的消息也不会事后补选。停用、到期或编辑广告只影响后续新消息。

“收件与回执”的详情展示广告决策、排除原因和最终组合正文。没有目标群时显示“未下发成功”，本条消息结束处理；之后补群不会自动补发，后续新消息正常使用当前目标配置。

## 即时消息与发送结果

从“消息接收管理 → 即时消息与发送结果”查看消息当前进度、目标投递数量、等待位置、原因、持续时间和系统下一步。仅系统管理员可查询，不选择工作空间。

“目标投递”按通道 × 目标群计数。例如手机向两个群下发显示共 2 项；同一群手机换机仍只算一项；全部手机模式也保留一个群目标，展开查看各手机独立结果。处理中涵盖调度、设备接收、设备执行及等待官方结果，各阶段会在“当前关注”中分开展示。

“通道已受理”只保留在展开后的时间线，表示任务创建完成。消息主状态随目标事实显示下发中、发送中、部分完成、全部成功、全部失败、已结束（部分失败）或结果待核对，不再永久停留在通道已受理。没有目标群或检查拦截时显示未下发成功；目标尚未生成时不显示全部成功。

定位长期未结束的消息：

1. 在“当前关注”查看停留位置、受影响群数量、原因及最近进展时间。通过通道、阶段或关注类型筛选；正常等待、自动重试和需要关注分开展示。
2. 展开消息，查看接收、内部交接和通道受理时间。目标明细给出冻结群名称、当前手机或发送身份、当前尝试和结果截止/调度时间；两类通道并行执行。
3. 点击目标行“查看任务与尝试”查看对应通道记录。手机历史未知结果单独提示风险，当前候选继续处理，不等待原手机恢复。
4. 显示“持久汇总待更新”时，列表计数仍依据当前持久目标事实；系统会定期校准汇总。明细和列表版本不同时使用“同步刷新”后核对，不重发来源消息。

手机尚未回报时，页面只显示等待接收或最终执行结果，不猜测本地正在操作哪个界面。明确超时后仍无后继推进会提示系统管理员检查自动调度；不把该观察提示作为新业务审批。观察信息不完整时显示“进度暂不可确认”，不能据此判定发送失败。

配置变化不改变已冻结消息，也不触发内容回撤、授权撤销、版本替换或旧消息补发。手机仍按原授权候选、业务额度和单次签名执行包调度：离线或明确失败立即换机，接收后五分钟没有最终结果切换下一授权候选；可能出现跨手机重复。企业微信结果以官方实际反馈为准，结果不确定时保留证据核对，不盲目重发。

在接收配置内可直接添加接收群：手机分发填写一个群名称；企业微信选择已同步的客户群。再选择候选手机或发送账号并保存启用。系统自动安排内部存储，不要求先创建或加入工作空间。启用配置同时明确授权所选手机与目标群的自动发送关系；手机实际业务额度与单次执行许可继续生效。

## 接收配置的群与手机分发方式

群接收方式可选“全部群”或“轮询一个群”；固定群只选择一个群即可。群和手机都按列表顺序轮流分配，可使用上移、下移调整顺序。手机下发方式可选“轮询首选并自动换机”或“全部手机分别执行”。企业微信的发送账号策略保持原规则。

轮询进度在分配新消息时持久推进，与最终反馈分开。G1、G2、G3 对应连续消息依次选 G1、G2、G3、G1；手机 A、B、C 同样循环。每条消息每个配置只预留一次手机首选，各群共享该起点，再按各群合法候选独立调度。首选 A 失败后由 B 接替成功，不会改写已经预留给下一消息的首选 B。并发消息按系统分配顺序占位，不等待上一条成功，不承诺最终到达顺序。

配置变更只影响新消息，刷新、重启与启停不重置进度。下一项被删除时继续原顺序中仍保留的后继；全部替换才从新首项开始。页面显示的下一起点是读取时参考，并发消息可能先占用。

“全部手机”是配置内明确选择的全部手机，不是系统所有手机。每台手机对本条选中的每个群分别发送；可能向同一实际群发送多次，启用摘要明确说明。手机各自回报成功、失败和未知，不能由 B 的成功抵扣 A 的失败，也不能将指定手机任务改派给其他手机。每项继续遵守真实授权、单次执行能力、物理锁、额度和有界预算，离线不阻塞其他手机。

在“即时消息与发送结果”展开消息，查看“手机独立投递结果”。分别显示群数、应执行项数、已生成项数和各类结果；大集合自动分批创建，无需人工处理。全部手机项成功才算本群完成，部分成功可在管理页查看。来源回执仍按群显示原有 pending、sent、failed、unknown 摘要：尚有活动项为 pending；全部成功为 sent；全部结束后有未知为 unknown，否则未全部成功为 failed。

可以停止本消息的全部手机下发或只停止一个群，停止阻止后续可控签发，不撤回手机已持久保存的包。迟到结果仍按原手机与尝试入账。查询、翻页、刷新不会重发或重置进度。


手机接收配置的业务方案按单位独立维护，可选择专属方案或恢复默认；未配置时采用默认规则。默认规则由“默认手机群消息业务方案”维护，各单位分别累计业务额度。资源范围仍由本页群与手机配置决定，不需要再次办理使用范围开通。方案变更不会追溯修改已经交付的签名执行包。
