# 企业微信规则配置与多群顺序执行

本手册说明已编码的企业微信 v3 配置与执行流程。真实企业微信规则、人工操作基准、APK 和真机发送仍待验收；合成 fixture 不代表支持真实客户端。设备凭据、单次资格和共享账本的通用约定见 [手机执行接口](mobile-delivery.md)。

## 身份与配置边界

企业微信所有业务 ID 和控件 ID 在 Otter 中均按不可用处理：不以企业、账号、群、成员、消息 ID 或 `resource-id`、`viewIdResourceName` 定位或证明身份。WeKeeper 内部 UUID 仅用于关联、授权、幂等与审计；Android 包名与版本仅用于识别安装环境。

账号使用企业名、账号名及可选辅助文字；群使用完整群名、内外部类型及可选群主资料。修改资料提升版本并使旧核验失效，必须重新人工核对。完整群名“机器人测试”不包含显示在标题后的成员数 `(2)`；只在已配置的标题槽中解析人数，不全局删除群名中的括号数字。同名群无法凭可见资料消歧时阻断。

v3 规则、时间政策和人工基准由平台「手机设备与发送账号」中的「规则与政策中心」维护，不写入 APK 的企业微信模板。支持精确包名、versionName/versionCode 和学校/设备发布范围；版本区间、多种签名/语言条件及引擎未支持的新动作不在当前能力内。

## 配置、验证与发布

1. 在隔离环境验证迁移 `202610290001_visible_delivery_strategies.sql` 与 `202610290002_configured_ordered_delivery.sql`。保持新执行关闭，部署兼容后端与 Web；不新增服务，也不改写旧 migration。
2. 在规则中心以声明式 JSON 创建不可变版本，录入页面、非 ID 节点条件、角色、有界导航图、消息状态、精确安装环境、业务政策及人工基准。修改既有配置时复制为新版本，可与原文对照。
3. 配置账号/正文冷却、统计窗口与额度、目标数、默认/最小群间等待、会话时长、输入节奏、页面/观察超时和人工样本下限。阶段时间及群间等待不得低于已审核人工基准；有效额度取发布政策与账号/群独立配置的较小值。
4. 补齐非 ID 节点样本和人工计时依据，按 `minimum_manual_samples` 采集有效样本。静态截图不能证明节点层级、返回路径或实际耗时。真实规则不能从合成 fixture 推定。
5. 将版本发布到明确学校及可选设备范围，复制完整发布 JSON，在 Otter debug 原生采样页只读试匹配。手动打开各页，核对页面分类和角色匹配数量；`actions_executed=0`，不导航、不输入、不发送、不上传原始聊天树。
6. 完成授权测试设备的配置匹配、APK 及发送验收，再开放对应环境。已有版本可重新发布用于回退；撤销发布会阻断后续资格，不代表撤回已发生的点击。

校验拒绝未知字段、外部/控件 ID、脚本、坐标、未知 schema/能力、缺失角色、不可达页面和指向发送角色的导航边。界面文字、层级和中间页变化在现有声明式能力内可只更新后台规则；新增操作能力仍需升级引擎。

## 登记目标与确认执行

1. 平台管理员登记并人工核对可见账号；学校管理员登记并核对可见群，建立账号与群授权，绑定并启用指定手机。平台身份不能替代学校权限。
2. Otter 选择企业微信并登记 v3 能力。启动先恢复旧请求与结果，读取实际安装环境，解析并校验唯一兼容发布，再构造无障碍适配器。缺少配置、摘要/能力/安装版本不符均阻断。
3. 学校策略选择单群或多群模式。多群使用不重复的有序目标，可逐个添加、移除、上移、下移；选择发布配置和群间等待。间隔可延长，不能低于有效政策和人工基准。保存或启用策略不发送。
4. “执行一次”以 `Idempotency-Key` 和 `expected_revision` 创建一个 run、一个草稿 task 和每群独立 item。目标顺序、共同正文、设备/资料版本及配置均冻结；同 key/body 重放返回原 run。
5. 预览逐项核对完整群名、顺序、正文、配置、等待、基准和限制。v3 确认声明为“同一正文仅向本次所列各群发送一次”；旧任务仍保留各群正文实质差异确认。未人工确认的草稿不可领取。

同文授权只覆盖本 run 内不同目标群，不豁免跨 run、同群、跨渠道去重或 unknown 占用，也不免除正文冷却。策略修改不改变既有 run。

## 逐群推进与等待

同一设备/账号按确认顺序由一个 run 占用，等待期间不穿插普通任务、不提前领取下一项 permit。每项分别执行 claim → prepare → permit → 单次 invocation → result。仅当前群可领取，不能跳群。

服务端接受成功回执后，在同一事务更新 item、账本、事件、完成时间与游标。下一群最早开始时间取完成时间加群间隔、账号冷却及正文冷却的最晚值；其他资格仍须检查。重复结果不重复推进。这里的“开始”包含退出上一聊天和搜索下一群。

Otter 先持久化 ACK 进度与等待锚点，再删除固定结果 outbox。设备使用单调时钟，收到 ACK 后至少等待完整群间隔；服务端 `next_eligible_at` 也必须到期。进程/会话重启保留等待，设备重启重新建立一次完整间隔；等待期间不操作下一群页面。会话时长来自政策，到期需人工再次启动，不自动创建新会话。

执行历史展示逐群结果、当前位置、最早时间、暂停原因和执行修订。task 的 `completed` 仅表示处理结束；只有所有群均有明确成功结果才显示全部群已确认发送。

## 异常、修订与回退

| 情况 | 处理 |
| --- | --- |
| 找不到群、同名、已有草稿、错账号、未知页面 | 停在当前项，人工处理后重新核验，不自动跳群 |
| 结果未确认、unknown 或旧资格未决 | 停止向后推进，只补报原 key/body，不重新点击 |
| 人工核对为已发送 | 保留成功去重，以核对接收时间建立保守等待锚点，显式恢复后继续 |
| 人工核对为未发送 | 停止本批后续自动执行、取消未执行项并保留清单；不整批重发 |
| 发布新版本替代旧版本 | 在途 run 保留冻结配置，启动优先解析该配置，不热换规则 |
| 原配置不再适用 | 先关闭旧 claim；只有无活动 claim、无任何 permit 的剩余排队项可预览并确认执行修订 |
| 停止、撤销或回退 | 阻止后续资格，保留已发生/可能发生动作的补报与核对，不清库 |

修订保留原目标、顺序、正文、已完成前缀、旧快照与操作者依据，不创建第二个 run，不缩短已承诺的最早时间。顺序任务拒绝原整策略重发入口。

## 接口与源码入口

管理接口仍使用 `/api/v1` 的 Cookie/Origin/CSRF 和学校/平台授权；设备 v3 使用专用 Bearer。写操作保持幂等键及相应版本/预览摘要校验。

| 路径 | 用途 |
| --- | --- |
| `/api/v1/platform/execution-configurations`、`/{id}` | 查询、创建及读取不可变配置 |
| `/api/v1/platform/execution-configurations/{id}/releases` | 发布到学校/手机 |
| `/api/v1/platform/configuration-releases`、`/{id}/revocations` | 发布历史与撤销 |
| `/api/v1/schools/{school}/configuration-releases` | 选择学校可见发布 |
| `/api/v1/schools/{school}/mobile-delivery-runs/{id}` | 逐群进度 |
| 同上 `/revision-previews`、`/execution-revisions` | 剩余项修订预览和确认 |
| `/api/v3/device-execution/configuration-resolutions` | 根据实际环境解析兼容配置 |
| `/api/v3/device-execution/configuration-releases/{id}` | 授权下载发布内容 |
| `/api/v3/device-execution/...` | 配对、会话、claim、准备、permit、结果和恢复 |

声明与事务实现分别在 `backend/src/distribution/domain/mobile_delivery/configuration.rs` 和 `backend/src/distribution/south/adapter/postgres/mobile_delivery/configured.rs`。共享类型位于 `api-contract/src/modules/mobile-delivery/configuration.ts` 和 device-execution 模块；`mobile-configuration-v3.json`、`mobile-configured-claim-v3.json` 仅是合成契约样例，不入库、不自动发布。

数据层保存不可变配置与发布、有序 targets/items、run 进度和追加执行修订；`delivery_content_scope_owners` 将同文归属限定到本 run，`delivery_execution_defaults` 保留旧执行路径初始冷却/统计窗口。保留全部历史 migration、正文归属和共享账本，不通过回滚表结构恢复旧发送能力。

2026-10-29 的编码验证：`make check-web` 全量通过（共享契约 48 项、Web 49 项及小程序相关检查/构建）；使用已安装 Rust 1.97.1 工具链的 `make check-backend` 通过（41 项通过、33 项依赖隔离数据库的测试忽略）。devbox 包装进程在当时沙箱中遇到权限错误，实际检查使用其已安装工具链直接运行。

PostgreSQL 17.11 单用户临时库执行全部 forward migrations、合成正文归属事务回滚测试及 179 条 SQL PREPARE 解析/规划检查通过。监听 socket 受限，未运行 SQLx 集成测试；这些结果不能替代事务并发及 HTTP→数据库集成验收。

发布前仍须在专用隔离库运行 `make test-integration`（显式设置 `WEKEEPER_TEST_DATABASE_URL`），验证确认并发、跨渠道占用、顺序边界、修订/撤销、unknown 与人工核对。另须完成真实配置/人工基准、Otter APK/签名/仪器测试，以及单群、双群、多群、长等待、重启和“APK 不变只更新规则”的受控真机验收。当前没有真实企业微信发送验收结论。

建议发布顺序：迁移 → 后端与 Web → Otter APK → 真实配置和只读试运行 → 授权真机验收。回退保留结果、核对和历史配置读取能力，不卸载清库或重写旧 outbox。
