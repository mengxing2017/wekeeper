# 数据库初始化基线

2026-10-31 按不兼容旧数据库的要求，将原有 14 份增量 SQL 合并成 4 份初始化基线。SQLx 启动时按版本号执行，只在首次初始化时建表；正常重复启动校验账本后跳过已成功的迁移。

| 顺序 | 文件 | 内容 |
| --- | --- | --- |
| 1 | `202610310101_core_business.sql` | 元数据、身份、学校、社区、企业微信目录、公共别名及历史记录 |
| 2 | `202610310102_broadcast.sql` | 官方群发、帖子和文本来源、批次及操作账本 |
| 3 | `202610310103_mobile_execution.sql` | 手机凭据、业务身份、发送许可/结果账本、规则与多群顺序、配对及索引 |
| 4 | `202610310104_automation.sql` | 多应用流程、维护与授权、v5 计划/投递/失败及共享正文归属触发器 |

4 份基线必须一起部署。手机发送归属函数依赖 v5 表，故在最后一份脚本末尾统一建立函数与触发器。不要在应用初始化全部完成前开放业务。

合并时将最终字段与约束直接写入创建语句，去掉旧数据回填、协议范围反复替换、过时索引的先建后删，以及旧版正文归属函数的重复定义。保留业务使用的历史记录结构和各协议账本；不做旧数据库的结构/账本自动转换。序列 `legacy_public_id` 归属 `legacy_aliases.public_id`，避免删表后留下孤立序列；已有残留序列不会被重置计数。

## 使用边界

- 当前基线要求空白 schema。旧分段脚本建立的数据库必须完整重建，不能只清空 `_sqlx_migrations` 或只删除表。
- 允许清空全部业务数据的 Compose 开发库，在仓库根目录运行 `make reset-dev-database`。它删除并重建整个 `public`，会清空业务数据、函数、序列与迁移记录，再启动 API/Web。
- 外部数据库由管理员重建专用数据库/schema；应用角色须拥有建表权限。API 不会自动清库，不会忽略 checksum 或迁移缺失错误。
- 此次合并完成后，后续修改使用更大且唯一的版本号前向新增迁移；不要原地修改已应用的基线。

## 验证

常规检查运行 `make check-backend`。隔离数据库测试仅使用显式 `WEKEEPER_TEST_DATABASE_URL`，运行 `make test-integration`；其中覆盖编号唯一、正常重复启动保留记录，以及残留函数/序列不阻止初始化。

此次合并在隔离 PostgreSQL 17 中对原 14 份 SQL 与新 4 份 SQL 分别建库，对比了 1,643 条目录记录：表、列及顺序、默认值、约束、索引、视图、函数、触发器、序列归属和初始数据完全一致。目录对比不能替代事务并发和 HTTP 集成验收；完整集成测试仍需可监听数据库的环境。
